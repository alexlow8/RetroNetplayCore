// ==============================================================================
// PHASE 4: IMPLEMENTATION GUIDE - HANDSHAKE + ROLLBACK NETPLAY
// ==============================================================================
//
// OVERVIEW:
// This phase implements the complete netplay system with two parallel paths:
// 1. ROLLBACK PATH: For cores supporting serialization (Snes9x, Genesis, etc.)
// 2. FRAME-SYNC PATH: Fallback for cores without serialization
//
// Both paths share:
// - Handshake mechanism (Phase 4B)
// - Input protocol (Phase 4A - already defined in PHASE_4A_INPUT_PROTOCOL.md)
// - Capability detection (Phase 4B)
// - Conditional logic based on core capability
//
// Status: Phases 1-3 ✅, Phase 4A Protocol ✅, Implementation ready
//

// ==============================================================================
// ARCHITECTURAL OVERVIEW
// ==============================================================================
//
// THREAD MODEL:
//
//   Frame Thread (60 FPS, Zero Allocation):
//   ┌─────────────────────────────────────────────────────────────┐
//   │ Main Loop (Program.cs)                                      │
//   │ 1. Load local input from controller                         │
//   │ 2. Call networkManager.PublishLocalInput(frameNumber, input)│
//   │ 3. Call inputs[] = networkManager.GetFrameInputs(frameNumber)
//   │ 4. Execute frame with inputs[]                             │
//   │ 5. Render                                                  │
//   │ ⚠️  MUST NOT ALLOCATE MEMORY                               │
//   └─────────────────────────────────────────────────────────────┘
//
//   Network Thread (Runs continuously, background):
//   ┌─────────────────────────────────────────────────────────────┐
//   │ NetworkThreadManager.NetworkThreadLoop()                   │
//   │ 1. Poll UDP sockets (non-blocking, 100ms timeout)          │
//   │ 2. Receive P2P messages from peers                         │
//   │ 3. Parse and store in ring buffer (or trigger rollback)    │
//   │ 4. Dequeue and send queued local inputs                    │
//   │ 5. Send heartbeat to server                                │
//   │ ✅ Allocations allowed (not frame-critical)                │
//   └─────────────────────────────────────────────────────────────┘
//
// DATA FLOW:
//
//   INPUT PATH:
//   Frame Thread → PublishLocalInput() → OutgoingQueue
//                                            ↓
//   Network Thread → Dequeue → Serialize → UDP Send → All Peers
//
//   RECEIVE PATH:
//   UDP Receive → Network Thread → Deserialize → Ring Buffer
//                                       ↓
//   Ring Buffer → GetFrameInputs() → Frame Thread

// ==============================================================================
// NOTES & WARNINGS
// ==============================================================================
//
// ⚠️  Zero Allocation Constraint:
//     - Frame loop MUST NOT allocate memory
//     - All buffers pre-allocated at startup
//     - GC collections = frame drops (bad!)
//
// ⚠️  Thread Safety:
//     - Ring buffer: single-writer (network), single-reader (frame)
//     - Outgoing queue: frame thread enqueues, network thread dequeues
//     - Use lock-free queue if possible, or simple lock for outgoing
//     - Use CriticalSection or SpinLock for minimal contention
//
// ⚠️  Rollback Complexity:
//     - Only works if core implements serialize/unserialize
//     - State size can be large (1 MB for N64)
//     - Snapshots every 10 frames = ~6 KB/frame at 60 FPS
//
// ⚠️  Network Assumptions:
//     - Frame rate = 60 FPS (16.67ms per frame)
//     - Typical latency: 10-50ms (LAN), 50-200ms (internet)
//     - Timeout: 50ms for frame-sync, 500ms for rollback
//
// ⚠️  Libretro Integration:
//     - Each core may have different input layout
//     - StandardInput format is a baseline
//     - Some cores need core-specific extensions
//
// ⚠️  Error Recovery:
//     - Checksum mismatch = drop packet (don't corrupt state)
//     - Handshake timeout = warn but continue (some peers may be slow)
//     - Late peer join = reject for now (can extend in future)
//


// ==============================================================================
// QUESTIONS FOR IMPLEMENTATION
// ==============================================================================
//
// 1. Outgoing queue: Lock or lock-free?
//    Recommendation: Simple Queue<T> with lock (simpler than lock-free)
//
// 2. Rollback trigger: Who decides to rollback?
//    Answer: Frame thread detects via flag set by network thread
//
// 3. State save timing: Every frame or every 10?
//    Answer: Every 10 frames (reduces memory churn)
//
// 4. What if peer state is different size than expected?
//    Answer: Reject and log error (memcpy would overflow)
//
// 5. What if core doesn't have serialize on startup?
//    Answer: Continue with frame-sync-only mode (acceptable fallback)
